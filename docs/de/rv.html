AI Coding Literacy

Review

Ergebnisse systematisch pruefen

Review bezeichnet die systematische Pruefung von generiertem Code gegen die definierten Anforderungen. LLM-generierter Code sieht oft korrekt aus, enthaelt aber systematisch Fehler. EvalPlus zeigt: Pass-Raten sinken um 19-28.9% bei gruendlicherem Testing. Vertrauen ist gut, Pruefen ist besser.

Theorie

Kernpunkte

  • EvalPlus: Pass-Raten sinken um 19-28.9% bei gruendlicherem Testing
  • Tambon et al.: 10 Bug-Patterns in LLM-generiertem Code

Konzepte

Halluzinierte Objekte

Nicht existierende Funktionen oder Bibliotheken, die das LLM erfindet

Intent Conflicting

Code widerspricht der Anforderung - macht etwas anderes als gewuenscht

Context Inconsistency

Code widerspricht dem bereitgestellten Kontext (Beispieldaten, Dokumentation)

Metamorphic Testing

Paraphrasierte Prompts zur Konsistenzpruefung - erkennt 75% fehlerhafter Programme

Traceback

Die Fehlerspur, die zeigt, wo der Fehler aufgetreten ist - von unten nach oben lesen

Logischer Fehler

Code laeuft, aber das Ergebnis ist falsch - am schwierigsten zu finden

Die 5 Halluzinationskategorien

Kategorie 1

Intent Conflicting

Der Code macht etwas anderes als gefordert.

  • Gefordert: "Sortiere absteigend" - Code sortiert aufsteigend
  • Gefordert: "Nur .jpg" - Code verarbeitet alle Bildformate
Kategorie 2

Context Inconsistency

Der Code ignoriert den bereitgestellten Kontext.

  • Beispieldaten haben Spalte "ID" - Code erwartet "id"
  • Dokumentation sagt UTF-8 - Code verwendet Latin-1
Kategorie 3

Dead Code

Code, der nie ausgefuehrt wird.

  • Funktionen die definiert aber nie aufgerufen werden
  • Bedingungen die immer wahr/falsch sind
Kategorie 4

Knowledge Conflicting

Widerspruch zu allgemeinem Wissen.

  • Falsche API-Signaturen
  • Veraltete Syntax
  • Erfundene Bibliotheken
Kategorie 5

Halluzinierte Objekte

Komplett erfundene Dinge.

  • import fictional_library
  • pandas.magic_transform() - existiert nicht

Uebungen

RV-1

Fehlermeldungen lesen

Tracebacks verstehen und die Ursache lokalisieren.

Lernziele: Tracebacks von unten nach oben lesen, die relevante Zeile identifizieren, Fehlertypen unterscheiden.

Aufgabe: Lassen Sie vom LLM Code generieren und provozieren Sie absichtlich einen Fehler. Lesen Sie den Traceback und lokalisieren Sie das Problem.

RV-2

Systematische Code-Pruefung

Eine Checkliste fuer LLM-generierten Code durcharbeiten.

Lernziele: Systematisch statt intuitiv pruefen, typische LLM-Fehler erkennen, eigene Checklisten entwickeln.

Aufgabe: Nehmen Sie Code aus einer vorherigen Uebung und arbeiten Sie die Checkliste durch.

Vertiefung

Die drei Testfaelle

Jeder Code sollte mindestens mit diesen drei Szenarien getestet werden:

Normalfall

Typische, erwartete Eingabe. "Das sollte funktionieren."

Grenzfall

Extreme Werte: leere Liste, sehr grosse Datei, Sonderzeichen, Umlaute.

Fehlerfall

Ungueltige Eingabe: Datei existiert nicht, falsches Format, fehlende Rechte.

Metamorphic Testing

Eine einfache Technik um LLM-Konsistenz zu pruefen:

  1. Stellen Sie dieselbe Anfrage mit anderen Worten
  2. Vergleichen Sie die Ergebnisse
  3. Bei unterschiedlichen Ergebnissen: mindestens eines ist falsch

10 haeufige Bug-Patterns (nach Tambon et al.)

  1. Off-by-one - Schleife laeuft einmal zu oft/zu wenig
  2. Missing Null Check - Keine Pruefung auf leere Werte
  3. Wrong Operator - = statt ==, > statt >=
  4. Type Mismatch - String statt Integer, etc.
  5. Hardcoded Values - Feste Pfade, die nur lokal funktionieren
  6. Missing Error Handling - Keine try/except
  7. Resource Leak - Dateien nicht geschlossen
  8. Race Condition - Bei paralleler Verarbeitung
  9. Incorrect API Usage - Falsche Parameter, veraltete Syntax
  10. Security Vulnerabilities - SQL Injection, Path Traversal
